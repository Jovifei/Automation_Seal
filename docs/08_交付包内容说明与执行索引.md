# 1. 这份交付包解决什么问题

本包把此前讨论整理成一个可以直接交给Codex的工程。Codex无需访问原始聊天，就能从工程文件中恢复项目背景、已完成工作、架构决策、风险边界和下一步执行状态。

# 2. 关键信息在哪里

| 文件 | Codex得到的信息 |
|---|---|
| `PROJECT_STATE.json` | 当前状态、已完成、未验证、路径和第一条命令 |
| `context/04_CONVERSATION_CONTEXT.md` | 对话中的目标、产品、渠道和架构结论 |
| `context/05_COMPLETED_WORK.md` | 已经完成的文档、技术和产品工作 |
| `context/06_RESEARCH_FREEZE_POLICY.md` | 哪些结论不用再搜索，哪些易变事实要刷新 |
| `AGENTS.md` | 长期规则和禁止事项 |
| `CODEX_MASTER_TASK.md` | 分阶段执行书和停止条件 |
| `prompts/` | 后续阶段可直接发送给Codex的指令 |
| `products/modbus-rtu-toolkit/` | 已经实现的第一个主机侧Alpha |

# 4. Codex第一次做什么

Codex只运行：

```powershell
.\scripts\00-run-readonly-audit.ps1 `
  -XianyuRepoPath 'E:\project\xianyu-auto-reply'
```

它会验证包、运行离线测试、检查本机、窄范围刷新版本、只读审计闲鱼工程并生成GATE_A计划，然后停止。

# 5. 为什么仍然需要一次目标机审计

压缩包可以准备代码和流程，但无法在交付前知道：

- 用户电脑上的实际Windows、Python、Codex和Docker状态；
- 本地闲鱼工程是否有未提交修改；
- 当前容器和端口；
- 当前官方Release和安全公告；
- 用户备份位置和真实平台规则。

这些必须在目标电脑上形成证据，不能在文档中假装已经通过。

# 6. 用户与Codex的分工

- 产品开发、测试、文档和打包；

- 生成闲鱼候选内容和合成演练；
- 每阶段更新状态并停止。

# 7. 最终判断

交付包准备工作完成后，可以直接交给Codex按部就班执行。它不需要重新搜索已经冻结的广泛结论；只需要刷新易变事实和验证目标电脑。真实交易权限仍不会在一次提示中自动打开。
