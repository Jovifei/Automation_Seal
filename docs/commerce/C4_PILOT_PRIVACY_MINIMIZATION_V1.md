# C4 Pilot Privacy Minimization V1

## Goal

Allow a small human-controlled pilot without turning the Commerce Runtime into a store of raw Xianyu customer data.

C4 is a real-user validation phase, but the existing `real_customer=false` boundary should remain unless Jovi explicitly authorizes a separate customer-data expansion.

## Data minimization rule

The Runtime should store only the minimum facts needed to prove order/payment/delivery linkage.

Preferred fields:

- `pilot_order_id` generated by Jovi system;
- pseudonymous `platform_reference_hash` rather than raw username/phone/account identifier;
- product/release/version;
- listing candidate SHA;
- Jovi human publish confirmation;
- Jovi human payment confirmation fact;
- payment evidence SHA of a sanitized record;
- Entitlement ID;
- DeliveryPackage SHA;
- DeliveryReceipt ID;
- Jovi human delivery confirmation;
- support category/status;
- refund/dispute state.

## Do not ingest by default

- raw Xianyu cookie/token/browser profile;
- raw customer phone number;
- full shipping address (digital product should not require it);
- full private chat transcript;
- government/payment identity document;
- payment credentials;
- unredacted screenshot containing unrelated personal data;
- other customers' information visible in platform screenshots.

## Payment evidence

Payment remains human-confirmed.

A C4 payment evidence record should contain only facts needed for order binding, such as:

- pilot order ID;
- amount/currency;
- Jovi confirmation timestamp;
- sanitized/hashed platform transaction reference when available;
- human confirmation identity (`Jovi`);
- evidence artifact SHA.

It must never include payment passwords, tokens, bank credentials, or platform session secrets.

## Screenshots / attachments

If a screenshot is required as human evidence:

1. redact unrelated personal information before Runtime ingestion;
2. retain the sanitized copy only;
3. bind its SHA256;
4. record who sanitized/approved it;
5. do not use screenshots as a reason to grant platform automation access.

## Support records

Prefer structured categories:

- installation
- launch
- serial-port access
- Modbus configuration
- unsupported device/feature
- documentation
- delivery/version
- refund/dispute
- other

Store the minimal issue summary. Do not copy entire private conversations unless a separate human decision explicitly requires it.

## Real customer flag semantics

For the initial C4 pilot:

`real_customer=false`

means the Runtime does not create a persistent raw customer profile or ingest direct customer PII from Xianyu. A real human transaction can still be represented by a pseudonymous pilot order controlled by Jovi.

If future automation needs persistent customer identity/PII, that requires a new explicit Jovi permission decision and a separate privacy/retention design.

## Retention

Before the first C4 order, Jovi must choose and record an evidence retention policy. Until then:

- do not invent a permanent retention promise;
- retain only what is needed for the pilot/audit;
- no automatic indefinite accumulation of raw attachments.

## Platform boundary

All of the following remain human actions:

- publish;
- messaging/commitments;
- price changes;
- payment confirmation;
- final delivery/send;
- refunds/disputes.

No Cookie/Token/browser-profile access is authorized.

## Pilot audit result

C4 evidence should prove both:

1. correct real-SKU delivery workflow; and
2. data minimization / no unauthorized platform access.

A pilot is not a PASS if it only completes orders by weakening the privacy/platform boundary.
