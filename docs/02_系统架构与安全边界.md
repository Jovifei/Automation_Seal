# 当前系统架构与安全边界

**最后校准：2026-09-05**

## 1. 当前总体架构

```text
E:\project\jovi-automation
Governance / Decision / Audit Mirror / Specs / Cloud Reference
        |
        v
E:\project\jovi-medusa-commerce-v1
Medusa v2.19.0 Commerce Runtime
Product / Order / Payment Evidence / Entitlement / Receipt / Delivery
        |
        v
E:\project\jovi-modbus-diagnostic-toolkit-v1
First Real SKU / Product Source
        |
        v
C4 Human Pilot
Xianyu publish/message/payment confirmation/delivery/refund = Jovi manual
```

另有：
- `E:\project\jovi-commerce-engine-v1`：Legacy pure-Python Commerce，archive only；
- `E:\project\xianyu-auto-reply`：独立外部适配器，不是 Runtime 权威，不共享数据库/Cookie/Token。

## 2. 权威分工

| 领域 | 权威 |
|---|---|
| Governance / Human Decision / Audit index | `jovi-automation` |
| Product / Order / Runtime workflow | `jovi-medusa-commerce-v1` |
| Payment fact acceptance | Jovi Policy + Human confirmation |
| Entitlement / DeliveryReceipt | Jovi Policy |
| 第一 SKU 原始字节 | `jovi-modbus-diagnostic-toolkit-v1` |
| 真实闲鱼动作 | Jovi 人工 |

不得出现双写双权威，例如两个服务都可独立生成 Entitlement 或 Receipt。

## 3. Commerce 数据流

```text
Product Source
  -> qualification + SHA binding
  -> immutable DigitalRelease
  -> private DeliveryAsset
  -> deterministic DeliveryPackage
  -> evidence-bound Listing Candidate
  -> Order
  -> human-confirmed payment fact
  -> Jovi Entitlement
  -> DeliveryReceipt
  -> short-lived DownloadGrant
  -> human-controlled final delivery
```

### Entitlement 与 DownloadGrant

- `Entitlement`：持久的权利/所有权事实；
- `DownloadGrant`：短时访问能力，可过期/撤销，只存 token hash，不能创造 ownership。

## 4. 当前真实平台边界

C4 前以及 C4 首轮 Pilot 中，至少保持：

- `production_integration_allowed=false`
- `real_payment=false`
- `real_customer=false`
- `xianyu=false`
- `auto_delivery=false`
- `n8n_production=false`

这里的 `real_customer=false` 表示 Runtime 不把原始客户身份/PII 作为数据源；C4 可以有真人买家，但只保存最小化的订单/交付事实。

## 5. 平台与秘密隔离

Runtime / Governance 不读取或保存：
- Xianyu Cookie / Token / Browser Profile；
- 买家真实姓名、手机号、地址；
- 完整聊天；
- 原始支付凭据；
- 外部适配器 SQLite。

真实发布、消息、付款确认、改价、交付、退款全部由 Jovi 手工执行。

## 6. 产品源隔离

C3 建立了 `PASS_ZERO_WRITE` 原则：
- Commerce 不修改产品仓；
- 会生成缓存/日志的测试在 temporary clone/export 中运行；
- installer/ZIP/EXE 原始字节只读绑定 SHA；
- Commerce 只生成 deterministic wrapper 和交易侧证据。

## 7. 审计边界

- 实现 Agent 不得自审；
- Independent Auditor 使用新会话、只读、复算；
- Governance mirror 是索引，不替代本地 Runtime evidence；
- 历史 FAIL / stale package 保留；
- Human Decision 不由测试自动生成。

## 8. 网络与运行

当前 Runtime 的 synthetic/staging 管理服务应继续优先绑定 loopback；公网暴露、Storefront、Webhook、远程浏览器控制都不是 C4 首轮 Pilot 的必要条件。

Medusa session 在 production/staging 默认使用 secure cookie；本地 synthetic loopback HTTP 只通过显式 synthetic-only override 放宽，任何 real/production flag 组合必须 fail-closed。

## 9. 供应链

当前已采用：
- Gitleaks v8.24.0；
- Syft v1.20.0；
- SHA256 / source-tree / sidecar；
- SBOM / license / third-party notice；
- pinned Medusa v2.19.0。

Trivy、harden-runner、SLSA/cosign 等是后续增强，不阻塞 C4。

旧文档中的 Track P/Track I、X0-X4、review-queue→approved 流程是早期治理模型。其安全思想仍有效，但**不是当前 Commerce Runtime 主架构**。历史资料见 `docs/HISTORICAL_DOCUMENT_STATUS.md`。
